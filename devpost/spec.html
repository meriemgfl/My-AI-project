01 · In plain language

How this works

The app runs on this computer. React displays the pages, an Express server handles requests, and SQLite saves the products, questionnaire answers, and routines in one local file. The server uses SQL to find the products and JavaScript rules to build explainable suggestions.

Why use a database?

You wanted SQL to be part of the learning. The app's rows and joins are real, but SQLite stays small and local—no account or hosted service needed.

Why rules instead of live AI?

A transparent match score can show which concern tags matched. Product claims come from curated product information; the app does not invent benefits.

02 · From PRD to system

The core journey

  1. Open the app. React asks the API for saved routines and owned products.
  2. Choose products. The catalog is searched in SQLite; the person's expiry date is saved on a separate owned-item row.
  3. Answer the questionnaire. Concerns, day/night, clock time, and weekly frequency are saved locally.
  4. See suggestions. Express excludes expired items, compares concern tags, orders product categories, and returns the matched reasons and authored notes.
  5. Save one. The API writes a routine and its ordered product steps to SQLite.
  6. Return later. The same browser loads that saved routine from the local database.

Fit score: matching selected concerns ÷ selected concerns. It measures catalog-tag overlap only, not how well a product treats a condition. Combination details are shown only when a source-backed note was authored; otherwise the app says “Not assessed.”

04 · App parts

Components and API

React screens

Home/saved routines, questionnaire, product list/details, suggestion results, and routine detail. The API is the source of saved data.

Express API

/api/products, /api/owned-products, /api/profile, /api/suggestions, and /api/routines return JSON and validate submitted fields.

Matching rules

Use owned, unexpired products; prioritize catalog timing guidance; use preferences when guidance is absent; keep sunscreen last in daytime order.

SQL data access

Parameterized SQL lives in one module. First-run seed inserts curated catalog entries and never replaces user data on restart.

How recommendations stay understandable

Each returned routine explains which concern tags matched. Product benefits are copied from curated records, not composed by a model. Unverified ingredient combinations remain unknown; there is no promise that the rules catch every possible reaction.

05 · SQL model

Data and persistence

Five SQLite tables keep the reference catalog separate from a person's own items and saved routines. JSON text is used for small tag lists; routine steps and product ownership use relationships the learner can query with joins.

TableWhat it storesLink
catalog_productsName, brand, category, ingredients, price/currency, benefits, concern tags, usage notes, source URLOne catalog product can have multiple owned items.
owned_productsCatalog product ID, expiry date (nullable), date addedReferences one catalog entry; expiry belongs to the individual item.
profile_preferencesOne profile row: skin type, concerns, period, clock time, uses per weekFixed ID 1 keeps this a one-person local demo.
routinesSchedule, concern tags, fit score, created dateOne chosen suggestion becomes a saved routine.
routine_stepsRoutine ID, owned product ID, order, purpose textForeign keys connect the saved ordered steps.

The database is data/skincare.sqlite and is gitignored. It stays on this computer; there is no sync or backup in this proof of concept.

07 · Decisions and open points

What we have decided

Learner choices

React/Vite; phone-sized browser demo; SQLite and SQL as part of learning; starter catalog based on owned products; local persistence; product guidance before preference.

Kept small on purpose

One local profile, curated seed data, deterministic match rules, and no accounts or hosted services. This makes the full request-to-SQL-to-screen path visible.

Price estimates found on official product listings are in USD; choose the display currency during build. Prices do not affect suggestions. Product-specific skin guidance is informational, not diagnosis or treatment advice.

Other realistic failure points

If the database cannot be opened, initialize its schema and seed data and show a readable error. If there is no eligible product match, explain that and let the person adjust selections. Do not guess missing product information.
